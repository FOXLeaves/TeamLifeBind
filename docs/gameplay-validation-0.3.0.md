验证日期：2026-10-11。目标 Minecraft 26.3，Java 25、Gradle 9.8.1；平台版本沿用 [0.2.0 升级依据](upgrade-research.md)。本轮实现范围是规则卡、快速节奏和强化图腾平衡，规则与配置见 [玩法说明](gameplay-update-0.3.0.md)。

```powershell
python scripts/verify-resources.py

.\gradlew.bat bundleRelease --no-daemon --console=plain
git diff --check
```

- 冷却检查覆盖同队同 tick 仅一次成功、不同队独立、899/900 tick 边界、清理后重新救援、经典档无额外冷却和并发竞争。它验证共享状态组件，不等同于真人同时致死伤害测试。
- 资源校验通过：21 份共享文件、65 个 JSON/pack 元数据、10 个模组语言键、311 个公共语言键。
- 完整发行 ZIP 将四端 JAR、插件资源包和当前文档一起打包；归档中的版本、加载器元数据、共享类、Fabric 必需 Mixin 与资源包格式另行校验。公共类保持 Java 21 字节码。
- GitHub Actions 未远程执行；本机结果不替代远程 CI。

## Paper 菜单与救援集成代理

临时验证插件在实际 Paper 主线程调用项目代码，通过 **168 条断言**：

- 使用实际 Bukkit inventory/PDC 核对规则卡槽位 4，以及管理员节奏/图腾按钮槽位 45/47。普通玩家能读规则，复制管理员按钮后点击仍不能改档。
- 直接调用菜单点击分支，确认管理员两档循环、文件持久化，以及四次延迟菜单重开全部完成且权限正确；未知代理调用会失败。
- 通过实际命令分发调用 `/tlb rules`。公共 setter 保存配置，准备阶段拒绝切换，不改文件；开局选项复制后修改持久化字段不会改变本局节奏与图腾预设。
- 代理当前最大 HP 为 2/10/20 时，调用实际强化救援函数。平衡档在末地内/外分别设置总吸收 1/5/8 HP，再生 400 tick；经典档末地外 20 HP、吸收 V，末地内 16 HP、吸收 IV，再生 1,400 tick。
- 实际计时重置函数清空团队冷却；测试结束还原隔离服配置字节、内存字段和配方。

代理记录药效等级、持续时间、血量与 `setAbsorptionAmount` 参数，**没有真实 NMS 玩家属性钳制、伤害链、原生图腾复活或客户端 UI 操作**。经典档和低血量档的药效容量结合引擎源码核对，最终表现仍需真人验证。

## 图腾边界修复的证据与范围

- Bukkit `finalDamage` 和 Forge 最终伤害已经扣除吸收，救援致死判断改用 `health - finalDamage`。NeoForge Pre 事件在吸收之前，保留 `health + absorption - damage`。这些差异根据对应引擎/事件实现静态核对，不记为真实攻击事件通过。
- Paper 原生复活事件发生时 HP 已为 0，因此冷却/末地拦截不以 `isDead()` 排除目标；检查实际触发手槽，避免手持图腾绕过规则。
- Fabric 在原生死亡保护之前调用团队救援，允许尚未提交死亡的目标进入救援列表；必需 Mixin 使用独立包，避免拦截普通入口类的加载。其他模组的死亡保护物品保留原流程。
- 强化救援按目标吸收量选择足够的药效容量，然后设置精确总量。经典档原设计的末地外 20 HP 现在使用吸收 V；旧吸收 IV 只能容纳 16 HP。

## 尚待真人与完整对局验收

1. 四端真实客户端规则卡、动态物品 lore、合成与原生复活；当前旧箱子/地面物品在进入玩家库存后刷新，未遍历所有容器。
2. 两档节奏逐个触发 tick 的实际事件执行、事件关闭时不触发、每局仅一次发奖与连续两局重置。共享回归已核对预设数值，未在真实比赛里等待全部事件。
3. 同队两人同 tick 致死、换持有者/维度、冷却边界、断线重连、手持主副手普通/强化图腾；确认实际消耗与救援次数。
4. 血量同步开/关，2/10/20 HP 与经验增长，普通/禁复活维度连锁死亡、团队床和屠龙结算。
5. 至少 2 人全流程及 4 人 2 队对抗；再记录各档 10 局的局长、救援存活率、补给争夺率与 tick 耗时。当前未给出平衡胜率或性能提升百分比。
